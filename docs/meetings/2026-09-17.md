## System and responsibilities

Recording chips → routing board → FPGA board → KR260 → PC

Chip and routing side. The routing board brings chip signals to the FPGA board. Two detachable board-to-board connectors were discussed. Gerald will provide chip pin locations and reference designs; Howard and Zitong need to agree on the mating connections.

FPGA side. Howard’s main responsibility is the FPGA board. It receives and organizes chip data and forwards it over fewer signal lines. The two board designers should collaborate, especially on the less familiar FPGA support circuitry.

Downstream side. KR260 was named as the downstream platform and called the “MCU” in the meeting. Coordinate its interface with David and the FPGA firmware collaborator. The intended control path comes from this downstream platform.

## Agreed direction

Design tool. Use KiCad for the PCB work. Check version compatibility when opening the shared files.

FPGA baseline. The device discussed was Artix-7 XC7A35T, and Gerald agreed to use the referenced FPGA. Confirm the complete ordering code and package from that reference before finalizing the design.

Size and usability. Minimize the board and support components, with a preference for a compact rather than elongated shape. Users should be able to power it on without manually reprogramming it each time.

Power and fabrication. Place FPGA power circuitry on the FPGA board. Recording-chip power placement remains under review. JLC was the preferred fabrication/assembly option.

## Technical discussion and open questions

Chip-to-FPGA pin count. About 88 data signals and roughly 100–110 total signals including programming/control were discussed. These are estimates, not an approved connector pinout; the transcript contains inconsistent later numbers. Gerald’s actual pin map must settle the count and direction of each signal.

FPGA-to-KR260 link. USB-C was favored as a possible compact connector, with micro-HDMI as an alternative. Selection depends on the usable cable conductors and interface needs. No USB or HDMI signaling protocol was agreed. A downstream adapter board was also proposed.

Data aggregation. Combining chip outputs into two to four data lines was a design question, not a demonstrated capability or finalized lane count. The interface also needs to accommodate control and programming. The team must determine what the hardware and firmware can support together.

Configuration and storage. Local memory that loads the FPGA at startup was discussed as a way to avoid manual reprogramming after power-off. Memory selection, loading method, required pins and the downstream platform’s role remain open. Configuration storage and recording-data buffering need separate requirements.

Power and board layout. Required FPGA supplies and support components need a datasheet/reference-design review. Placement of recording-chip LDOs may change to reduce size. The dimensions quoted for the existing reference were approximately 23 × 23 for the FPGA and 60 × 50 for the board; these are not new-board targets. Final dimensions and layer count were not selected.

Future functions. High-pass and low-pass filtering were mentioned as possible future requirements from Chong. They were not committed as immediate deliverables.

## Questions to resolve in the next review

1. What complete FPGA part number and package will the design use, and what is the minimum circuitry needed to power, start, configure and operate it?

2. What is the exact chip-to-FPGA signal list, including data, timing, control and programming signals and their directions?

3. What data rate must the FPGA-to-KR260 link carry, and how many data and control lines does the chosen implementation require?

4. Which connector, cable and signaling scheme can both the FPGA firmware and KR260 support?

5. How will initial programming, automatic startup and later configuration updates work for the end user?

6. Where will recording-chip power regulation sit, and what dimensions and PCB layer count are practical?
