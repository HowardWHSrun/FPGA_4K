# Prior firmware: what can be reused for Artix-7 bring-up

26 September 2026 · read-only source review · no programming or code changes

**The repository already contains useful reset, SPI and capture examples. It does not contain a revision-identified startup program or timing constraints for the new eight-ASIC Artix-7 board.** The useful result is a concrete porting baseline, not a claim that all startup behavior is unknown.

The packaged reference is identified as [gt-ic/FPGA_512, commit 767e82528780005cbcb37b3e926197755bac622e](https://github.com/gt-ic/FPGA_512/tree/767e82528780005cbcb37b3e926197755bac622e) in `sources/README.md`. Its target is **LFE5U-25F-7BG256I**, one 512-channel ADC interface with eight serial DATA lines, one returned clock and FT600 USB. Eight DATA lines are not eight independently clocked ASICs. No silicon mask/ASIC revision identifier was found in the scoped source search. The historical known-good bitstream notes report tests on that earlier setup; those claims do not qualify current source changes or the Artix board.

## Do not transplant these behaviors unchanged

1. **Boot-clock dependency:** the old top drives `cb_clkh = clk_16m` continuously (line 96), while its command decoder and SPI programmer run from returned `cb_clk32mhz` (lines 208, 270). Gerald now requires SPI → digital/analog reset → start recording clock. With the recording clock stopped, a returned-clock-powered SPI controller may never run. Put the new startup/SPI controller in the **local 32 MHz reference domain**, keep capture domains separate, and start recording clocks only after configuration/reset completion. Use suitable FPGA clock-output resources and a glitch-free enable strategy when implemented.
2. **The advertised default SPI transaction is not reliably all zero:** `board_cmd.c:161–165` and `adc_daemon.c:613–619` only set length 4,096 and execute. They never clear/write SPI RAM. After a custom load they retransmit stored contents, and the RTL contains no portable RAM-zero initialization. A port must explicitly load every transmitted byte or select a defined constant source; do not rely on the comment that BRAM powers up to zero.
3. **Bound the actual buffer:** `spi_programmer.v:24` accepts a 13-bit count, but lines 42–43 and 65 provide only 512 bytes/channel and a 9-bit address. Counts above 4,096 wrap and repeat data. Reject unsupported counts, latch the accepted length, check that all required bytes have been loaded, and reject writes/reconfiguration while busy. Its current top leaves `busy` unconnected (line 277).
4. **Use an acknowledged command transfer:** the old FT600 crossing toggles on every command without a return acknowledgement (`top_4lane_framed.v:152–175`). It therefore depends on command spacing and payload stability. A new transport needs a proper handshake or asynchronous FIFO; do not assume USB call spacing is a general CDC guarantee.
5. **Do not turn decoder heuristics into the physical protocol:** `fpga/adc_auto_adjust.v:20–35,64–86` chooses offsets 11–13 from data bits. That is a reference-specific alignment heuristic. Gerald's slide waveform instead labels 16 padding clocks followed by 48 payload clocks, and the old code ignores SYNC. Preserve raw DATA/READ/SYNC and validate a known pattern before selecting a fixed decoder/channel map. The old README's 15.625 kS/s and the slides' 31.25 kS/s are also distinct claims; the former top outputs 16 MHz while the tutorial names a 32 MHz recording input.

## What the search did and did not close

The slides and source establish L/R direction, sample edge, candidate reset polarity, candidate inactive stimulation levels, a serializer structure and a CSV loading convention. These details should replace blanket “unknown” statements in a development plan.

No ASIC SPI workbook, gain/stimulation serializer, revision-labelled `BIT,L,R` payload or Jiaao-authored Artix timing constraints were found under the requested `firmware/` and `sources/` scope. Slide 26 shows a **2,124-bit example with a 12-bit DR configuration suffix**; this is not a complete machine-readable payload and differs from the older 4,096-clock zero-flush example. Existing `UWB_SPI/` Python controls the separate UWB device and is not the ASIC register map.

The reference [`adc_4lane_framed.lpf`](https://github.com/HowardWHSrun/FPGA_4K/blob/main/firmware/FPGA_512/adc_4lane_framed/adc_4lane_framed.lpf), lines 5–80 and 145, provides ECP5 pin assignments, LVCMOS15 and nominal clock frequencies. It supplies no ASIC min/max input/output delays and cannot be translated into qualified Artix constraints by renaming pins. Its treatment of AC_IN/IMP_TST as unused digital inputs must not override Gerald's analog AC_IN answer or the current documented IMP_TST assumption.

`sim/tb_h5.v` and `sim/extract_h5_stim.py` provide captured-pattern regression material. Their expected decoded values are computed by mirroring the decoder algorithm, so passing that test alone cannot validate the ASIC channel map or absolute timing. It remains useful stimulus for a separately checked raw-data or decoder test.

The remaining targeted integration input is therefore **the actual current configuration payload/generator and its chip/board revision**, together with pad timing limits and the eight-chip/shared-control contact topology. Continue implementable work from the reference-supported assumptions, but do not claim that the old ECP5 bitstreams, boot order, USB transport or masks are validated for this Artix PCB.
