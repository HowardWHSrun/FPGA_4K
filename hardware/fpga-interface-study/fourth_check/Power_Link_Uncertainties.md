# Fourth-pass power and link uncertainty register

26 September 2026. **No hardware was powered or tested. No manufacturing release is implied.** This pass freshly read the current native component manifests, current bring-up status and source hashes, challenged the third-pass electrical report, and checked the receiver pin/USB/power documentation. It did not rerun physical DRC or change CAD.

There is no newly demonstrated regulator-divider or power-pin fault in this scope. The remaining blockers are unresolved requirements, absent implementation and unmeasured qualification; those are different from a failed hardware test.

## Newly explicit transport gaps

1. **The proposed 6,165-byte frame needs a USB packing rule.** It is not divisible by four or sixteen. The XEM pipe interface uses 32-bit FPGA words and 16-byte host transfer multiples, so receiver firmware must aggregate/repack the byte stream or pad it deliberately. The link frame can remain unchanged. A direct one-frame 6,165-byte Pipe read is invalid. [FrontPanel API](https://docs.opalkelly.com/fpsdk/frontpanel-api/fpga-communication/).

2. **USB flow control is not ASIC flow control.** All fast pairs travel to the XEM; stopping a USB read does not stop incoming samples. At the proposed framed rate, a 100 ms stall needs 19.27 MB of buffering. Even the complete nominal 2 GiB memory would hold only 11.15 seconds before reserving any space; actual usable buffering is lower. A finite-stall and explicit overflow policy is essential. These are calculated capacity examples, not observed behavior. [FrontPanel performance](https://docs.opalkelly.com/fpsdk/performance/), [XEM memory](https://docs.opalkelly.com/xem8310/ddr4-memory/).

3. **The host-storage requirement is substantial and untested.** The proposed compact frames produce 693.56 GB/hour before storage overhead. Receiver bandwidth is only one part of the acquisition-to-disk acceptance test. [Performance guidance](https://docs.opalkelly.com/fpsdk/performance/).

## Verified boundaries and evidence

- Both manifests still identify J4 by a connector family, export different target references (3.3 V core versus 1.8 V rail revision), and leave the eight fast-link contacts unassigned. Contacts 4/7/10/13/16 and shell are GND. Four regulators still receive LINK_12V directly; proposed cable protection/damping is not native circuitry.
- Current `minimal_core` and `full_system` trees contain no link/receiver HDL or complete matching build. The only current-variant constraint source found is `full_system/bringup/core.xdc`. Legacy root material is correctly marked as incompatible with the compact boards.
- The official XEM map does expose multiple bank64 GC pairs. The four examples in PL-05 prove selectable resources exist; they are **not** a final pin assignment or proof of legal clock routing. Module PCB and package delays belong in the end-to-end timing budget. [Pin reference](https://pins.opalkelly.com/pin_list/XEM8310), [length-matching guidance](https://docs.opalkelly.com/length-matching-carrier-boards/).
- XEM8310 is an FPGA/USB module, not an automatic remote-JTAG programmer. Its dedicated JTAG connector targets its own FPGA; a remote GPIO master is additional logic. [Expansion documentation](https://docs.opalkelly.com/xem8310/expansion-connectors/).

[Machine-readable register, arithmetic and file hashes](Power_Link_Uncertainties.json) preserves the evidence and exact proposed closure criteria. [Third-pass electrical evidence](../triple_check/Electrical_Review.md) contains the existing rail, LVDS and JTAG corner calculations. Earlier 90 mV ground-offset and 5.2 W examples must retain their stated assumptions; they are not measured cable behavior or delivered power.

## Small external-information request

Only these system-specific facts require the lab or its ASIC/routing-board owner; the rest is engineering work that can proceed without asking the user to design the board.

- The actual ASIC/routing-board supply source, I/O electrical limits and legal startup/shutdown/pause behavior.
- Required acquisition/stimulation modes and command timing; required recording duration and what should happen if the computer stops draining data.
- Intended cable length, operating temperature/mechanical enclosure, and eventual computer/USB connection/storage for qualification.

The existing short-cable, 12 V and initial ambient proposals can remain provisional design targets while these facts are collected.
